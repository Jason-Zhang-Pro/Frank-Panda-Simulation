# Gazebo 三算法实测（2026-10-25）

## 实验条件

在同一 Panda / 27 碰撞体场景中，串行运行 RRT、RRT-Connect、RRT* 的完整抓放任务，每种使用种子 1、2、3；每次重启独立无 GUI Gazebo 世界。使用相同 URDF、障碍、夹爪、PD、碰撞裕量、shortcut 和 B 样条配置。每个全局搜索请求预算 5 秒，不是整个任务的时间预算；竖直段共用 IK＋约束 B 样条。

硬件为 Intel Core i7-14650HX，Linux / ROS 2 Humble，OMPL 1.7.0、MoveIt Core 2.5.10、FCL 0.7.0。工程 CMake Build Type 未指定；不将此结果当作不同优化等级下的性能上限。测试使用独立 ROS 域和 Gazebo 分区，原有 GUI 仿真保留运行；算法按种子交错执行，未控制 CPU 频率或消除全部后台负载。

RRT 使用单树扩展，RRT-Connect 使用双树连接，RRT* 使用选父节点和重连优化关节空间路径长度；三者复用同一碰撞场景和后处理。

本次先完成三包编译，再执行真实物理任务。任务成功只按 `pick_place_succeeded` 判定，要求实际抓取、放置、松开及归位，不能用“找到了路径”代替成功。

## 1. 同类接近段：搜索与路径长度

每次任务的第一个全局请求为从同一名义初始姿态接近同一方块，三算法均有 3 个有效样本。表中为算术平均；物理初始化与反馈存在微小差异，并非逐位相同的关节状态。长度是七维关节空间长度，单位 rad，不是末端米数。搜索时间来自 OMPL solve 日志；首解时间来自规划器中间解回调，无回调时用返回时间近似，精度低于完整计时追踪。

| 算法 | 接近轨迹生成成功 | 平均 solve 时间 / s | 平均首解时间 / s | 原始长度 / rad | shortcut 后 / rad | 长度缩减 |
|---|---:|---:|---:|---:|---:|---:|
| RRT | 3/3 | 0.3623 | 0.3623 | 5.2032 | 2.2211 | 57.3% |
| RRT-Connect | 3/3 | 0.0043 | 0.0043 | 2.3497 | 2.2212 | 5.5% |
| RRT* | 3/3 | 5.0106 | 1.2397 | 5.2032 | 2.2212 | 57.3% |

RRT* 在 5 秒预算内继续优化，所以 solve 时间较长不能简单等同于首解慢。当前样本中 RRT-Connect 的接近段首解较快；shortcut 后三者长度接近，说明后处理明显影响最终路径，不能把差异全部归因于搜索算法。该接近段不是最困难的携物通道。

## 3. B 样条与结果解释

所有正式任务使用相同的 shortcut＋B 样条配置。日志和 `phases.csv` 区分全局 `bspline`、抓放 `cartesian_bspline` 与回退类型。此次没有关闭平滑作物理消融，也没有记录足够高频的力矩/加速度以计算振荡 RMS 或 jerk，因此不提供“抖动减少百分比”或把定性平滑观察包装成定量结果。

初始接近段在 shortcut 后长度接近，但携物路径、接触和最终放置表现仍不同。当前更有依据的结论是：RRT-Connect 在本组设置下更容易得到可执行携物路径；整套抓放仍有放置到位稳定性问题，不能写成稳定完成率 100%。A* 仍是后续研究方向。

已有离线单查询工具保留为补充诊断；本页数据全部来自 Gazebo 中的完整任务尝试，未混用离线结果。

部分 Gazebo 进程在任务记录结束、收到退出信号后报告退出崩溃；该现象位于任务终止之后，原始日志已保留，关闭阶段的稳定性仍待排查。
